# 在庫管理システム 基本設計書

本書は、在庫管理システム（以下「本システム」という。）の基本設計を示す文書である。
対象読者は、開発を担当する技術者、および受入試験を実施する業務部門の担当者とする。
本システムは REST API で在庫サービスと通信し、JSON 形式の応答を受け取る。
応答が 200 以外のとき（タイムアウトを含む。）は、3回まで再送を行う。
なお、「再送しても失敗した場合」の扱いについては、4.2 節に記載する。

:::note

Webhook の受信側は、同一の `orderId` が2回以上届くことを前提に実装すること。
ネットワークの再送により、重複して届く場合がある。

:::

## システム構成

本システムは、次の3つの構成要素からなる。各要素は独立に配備でき、障害が発生した場合でも、
他の要素の稼働を妨げない設計とする（いわゆる疎結合）。

| 構成要素 | 役割 | 稼働環境 |
| --- | --- | --- |
| 受注 API | 外部の販売管理システムから受注を受け取る | コンテナ |
| 在庫サービス | 在庫の引当・解放・棚卸を行う | コンテナ |
| バッチ | 日次の締め処理と、翌日分の引当を作成する | 仮想サーバ |

:::warning

在庫サービスの応答は、必ずしも即時ではない。引当の要求を送った直後に在庫数を参照すると、
反映前の値が返ることがある（結果整合）。画面の再描画は、引当完了の通知を受けてから行うこと。

:::

## インタフェース

受注 API のエンドポイントを次に示す。認証は Bearer トークンによる。

```json
POST /api/v2/orders
{
  "orderId": "ORD-2026-000123",
  "items": [{ "sku": "A-100", "qty": 3 }],
  "requestedAt": "2026-09-20T10:00:00+09:00"
}
```

応答の `status` が `accepted` のとき、引当は非同期に実行される。
処理の結果は、Webhook（`POST /callback/orders`）で通知する。

## エラーコード

| コード | 意味 | 利用者への表示 | 再送 |
| --- | --- | --- | --- |
| E1001 | 在庫不足 | 「在庫が不足しています。」 | しない |
| E1002 | SKU が存在しない | 「商品が見つかりません。」 | しない |
| E1003 | 数量が上限を超えた | 「一度に注文できる数量を超えています。」 | しない |
| E2001 | 在庫サービスのタイムアウト | 「時間をおいて再度お試しください。」 | する |
| E2002 | 在庫サービスの内部エラー | 「時間をおいて再度お試しください。」 | する |
| E3001 | 認証トークンの期限切れ | 「再度ログインしてください。」 | しない |
| E3002 | 権限が無い | 「この操作は許可されていません。」 | しない |
| E9999 | 分類できないエラー | 「システム管理者に連絡してください。」 | しない |

## 非機能要件

1. 性能: 受注 API は、95パーセンタイルで 300ms 以内に応答すること。
2. 可用性: 平日 8:00〜20:00 の稼働率を 99.9% とする。
3. 保守性: 設定値は環境変数で与え、再ビルドなしに変更できること。
   - 秘密情報はシークレット管理サービスから読み込む。
   - 設定の変更は監査ログに残す。

:::danger

本番環境の在庫データを、検証環境へそのまま複製してはならない。
取引先名と単価が含まれるため、秘密保持契約に違反する。

:::

## 移行

移行は、既存システムを停止した状態で行う。停止時間は最大2時間を見込む。
移行の手順、および切り戻しの判断基準は、別紙「移行計画書」に定める。
詳細は [移行計画書](https://example.com/migration) を参照すること。
